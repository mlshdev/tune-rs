# Technical notes

## Architecture

SOCKS5 setup returns a typed TCP relay or UDP association guard; only authentication/request setup is subject to the 15-second handshake timeout. UDP controls then remain open until the client disconnects or the VPN stops. Monotonic association IDs own learned client endpoints and connected flows, so cleanup remains valid after lazy binding and an old guard cannot remove a replacement association after a reset. Client IPs are pinned to the TCP peer; explicit source ports are preserved. Outgoing sockets match the destination address family, and ownership is rechecked after async socket setup before a nonblocking send. Dropping a flow aborts its reply pump. The persistent UDP loop is polled inside the listener's future rather than detached, so server aborts drop its owned task tree.

`src/lib.rs` exports the typed networking and service modules; `src/main.rs` owns CLI parsing and process lifecycle. SIGINT/SIGTERM handlers register before network initialization so startup signals are retained. The runtime discovers default routes and local networks through `rtnetlink`, pre-binds health, control, DNS, optional proxy and metrics listeners, loads Mullvad server data, then installs an `inet tune` nftables ruleset before starting the WireGuard connection loop. Local-network policy rules and inbound/outbound routing tables are configured while the firewall is active. IPv6 reachability is probed using temporary output allowances. The process monitors health, DNS, control, metrics, proxies, VPN, relay updater, SIGINT, and SIGTERM; it stops background services and the VPN, then **seals** the firewall before tearing down policy routes: the deny-by-default chains, loopback, and LAN allowances stay committed while the namespace lives, while the VPN endpoint allowance, tunnel-interface acceptance, and temporary probe output allowances are dropped. Sealing exists because containers sharing Tune's network namespace keep it alive after Tune stops; an explicit `FIREWALL=off` remains fully off. Network teardown also runs when a service returns an error, and the nftables table finally disappears with the network namespace. DNS restoration leaves an unchanged resolver file untouched, allowing a preseeded read-only loopback resolver mount.

`src/vpn.rs` selects servers, brings up a kernel WireGuard interface via rtnetlink and `nl-wireguard`, optionally negotiates Mullvad's post-quantum ephemeral peer, checks health, measures path MTU when requested, and refreshes public IP information. A failed tunnel retries with exponential backoff. VPN input-port and endpoint allowances are removed on disconnect. `src/firewall.rs` atomically replaces nftables tables via libnftnl/libmnl and drops traffic by default when enabled. Accepting an inbound connection sets a dedicated conntrack mark (`Immediate` into a register plus `Conntrack::Mark`), and the OUTPUT `established,related` bypass requires that mark, so pre-existing clear-route connections cannot keep egressing in clear after the tunnel disappears. Global `FIREWALL_INPUT_PORTS` allowances expand to default-route interfaces only, matching gluetun; ports allowed on the VPN interface accept input without the mark, so their replies stay fail-closed at tunnel loss. `src/routing.rs` owns the additional policy rules and tables. `src/health.rs` serves a failing response until a check succeeds and resets that status when the tunnel stops.

`src/dns/` listens on UDP/TCP port 53 and forwards queries to plain DNS, DoT, or DoH using pinned preset IPs and authenticated TLS names, defaulting to Mullvad DoT. Replies are served only while the VPN is running. Positive replies have a bounded TTL-aware cache; name/IP blocks, rebinding protection, and periodically downloaded qdm12 blocklists are applied before delivery. `src/dns/system.rs` installs and restores `/etc/resolv.conf` within the container. The Compose stack supplies a loopback resolver file so default DNS does not require writing a root-owned Docker-generated file from the unprivileged app.

`src/httpproxy.rs` and `src/socks5.rs` implement tunnel-gated HTTP/CONNECT and SOCKS5 TCP CONNECT plus UDP ASSOCIATE. HTTP upgrades and upstream connection drivers are owned by each client's JoinSet, with a bounded task queue; dropping the listener task or changing tunnel status cancels the entire task tree, including pending handshakes and streaming responses. SOCKS5 UDP ASSOCIATE datagrams arrive on a second socket bound beside the TCP listener; associations bind lazily to the first observed datagram source when the request endpoint is unspecified, `SOCKS5_ALLOWED_CIDRS` filters datagram source IPs, and each `(client, destination)` pair gets a connected flow socket whose pump task re-wraps replies with a SOCKS header. Flows are bounded (512), expire after 60 seconds idle, and are aborted on tunnel status changes together with their associations; closing the TCP control connection unregisters its association and flows through a drop guard. Fragmented datagrams are dropped, and domain destinations resolve through the container resolver. Hop-by-hop and Connection-nominated headers are removed in both directions. `src/shadowsocks.rs` uses the core Shadowsocks encrypted TCP streams and UDP crypto functions, with at most 128 TCP clients, 128 UDP sessions, 512 connected outbound UDP flows, and 16 queued datagrams per flow. Flow inactivity expires after 60 seconds, session replay state after 120 seconds. AEAD-2022 sessions share replay windows, server IDs, and reply counters across destinations. Classic UDP salts are checked explicitly because the upstream UDP decryptor omits replay checks; the `security-replay-attack-detect` feature is required as well as a Reject policy. All relay tasks are tracked and cancelled on tunnel changes. No plaintext or unauthenticated legacy ciphers are accepted.

`src/control/lifecycle.rs` provides bounded, acknowledged commands and observable worker state. DNS stop/restart cancels and joins client/blocklist tasks and clears the cache before acknowledging; stopped listeners return SERVFAIL without forwarding. Updater stop cancels its download before acknowledgment, and a manual start works with scheduled updates disabled. `src/control/auth.rs` parses strict typed TOML roles and default-role JSON, redacts secrets, and checks exact method/path access. Configured role policies fail closed on unassigned routes. Legacy Bearer, X-API-Key and query-key authentication remain available. `src/control/vpnsettings.rs` translates supported Mullvad/kernel-WireGuard settings to the gluetun-shaped API. Partial changes are serialized, validated against configuration and the current relay list, then atomically published through a watch channel; a restart signal tears down the old tunnel before the VPN loop adopts the new settings. Redacted secret values preserve existing keys during GET/PUT roundtrips. `src/metrics.rs` exposes status/health/uptime and reads Linux sysfs traffic counters for the current configured interface, preserving gluetun's metric names. Missing interfaces report zero; unreadable or malformed statistics are logged and omitted. HTTP absolute-URI HTTPS forwarding uses the shared certificate-validating TLS connector; stealth controls X-Forwarded-For insertion.

`src/cli.rs` generates 128-bit random base58 API keys and formats bundled relay tables. The CLI also generates WireGuard keys, derives public keys, checks health, exports JSON/Markdown, and performs an explicit one-shot Mullvad update with the same validation and persistence path as runtime updates. Standalone updates do not configure a tunnel or firewall and use the caller's network namespace. Full live-VPN and compatibility validation still require final auditing.

## Mullvad relay updates and storage

`src/provider/select.rs` treats the configured country list as the primary ordering in both random and ordered modes. Hostname/city/ISP preferences and IPv6 preference never elevate a fallback country above an earlier country. A stable candidate pool is shuffled once per pool change in random mode; retry attempts do not reshuffle away failure history. The picker records endpoint-specific health/PQ failures, exhausts eligible endpoints in a country before proceeding to the next, and starts a new cycle when all endpoints fail. Startup health success clears prior failures, so a later reconnect checks the preferred country again. Local device/firewall setup errors are not attributed to a relay. Operator stop/restart resets the picker; changed relay pools invalidate old failure state. A healthy fallback remains connected until a reconnect is needed; no bandwidth probes or periodic preemption are performed.

Only Mullvad is representable by `ProviderName`; its singleton identifier preserves the existing manifest's `mullvad` key and settings response shape. `servers/mullvad.json` is the sole bundled provider dataset. Non-Mullvad manifests are ignored; provider selectors and aliases reject other VPNs. Tier/category/region/number/streaming/multihop filters and provider-specific address defaults are removed. NAT-PMP, gateway discovery, and nftables NAT/redirection support are removed; enabling VPN port forwarding fails configuration validation.

`src/updater.rs` fetches `https://api.mullvad.net/app/v1/relays` with normal HTTPS certificate validation, a 30-second timeout, no environment proxy, no redirects, and an 8 MiB body limit. Typed responses map active WireGuard relays to country, city, hosting provider, ownership, public key, and IPv4/IPv6 endpoints. Invalid keys, endpoints, locations, duplicate hostnames, empty lists, and excessive count reductions reject the complete update. Non-WireGuard relay sections are unused. No account token is needed.

Updates start only in `Status::Running`; status changes cancel in-flight downloads and the firewall remains deny-by-default. The initial refresh is immediate once running, successful refreshes wait `UPDATER_PERIOD` (default 24h), and failures retry after 60 seconds while running. `UPDATER_PERIOD=0` disables automatic scheduling, not manual API requests. Updates retain `keep` entries and respect preferred persisted lists. Storage writes run on a blocking worker, publish in-memory state only after persistence succeeds, and atomically rename each JSON file. Existing connections are not interrupted; subsequent connections use the new snapshot. This depends on a usable bundled or persisted relay for the first connection.

## Build and verification

Mullvad's `Classic-McEliece-460896f-round3` protocol requires `classic-mceliece-rust` 2.0.2, the latest round-3 release. Upstream 3.x changed to the incompatible NIST round-4 KEM, removing the round-3 ciphertext confirmation and changing the wire format from 188 bytes to 156. The manifest's 2.x compatibility constraint is intentional; do not upgrade it to 3.x, truncate ciphertexts, or bypass verification without a matching server-protocol migration. The regression checks the round-3 wire size and rejects a truncated round-4-sized payload. Upstream documents the change in its [changelog](https://github.com/Colfenor/classic-mceliece-rust/blob/v3.1.0/CHANGELOG.md). Dev-only Tokio `test-util` advances the test clock beyond the handshake deadline without waiting 15 real seconds.

Credentialed testing on 2026-10-19 exposed four defects missed by the original 130-test suite: round-3 McEliece incompatibility, IPv4-only UDP destination sockets, a handshake timeout spanning the entire association, and lost ownership after lazy endpoint binding. All four were reproduced by failing regressions before fixing them. The resulting 137-test suite passes strict clippy, formatting, and all ignored kernel/network tests. Live retests also verified actual PQ negotiation followed by IPv4/IPv6 Mullvad egress, SOCKS5 UDP IPv4/IPv6 DNS relay, an association surviving beyond 15 seconds, and rejection of further datagrams after TCP disconnect. No ciphertext truncation, verification bypass, or plaintext fallback was introduced. Detailed runtime validation and cleanup results are in `HANDOFF.md`.

Rust code using Linux netlink and libnftnl must be built on Linux. The development image is `dev-tune-rs-toolchain:local`, based on `docker.io/library/rust:1.98-slim-trixie` with `pkg-config`, `libnftnl-dev`, `libmnl-dev`, rustfmt, and clippy. The multi-stage `Dockerfile` selects the native GNU/Linux target from uname, rejects other architectures, stages the release binary at `/out/tune`, and copies it to `docker.io/library/debian:trixie-slim`. Local Docker commands use remote `homevm` (native linux/amd64); copy source to `/home/mlsh/dev/tune-rs` before bind-mounting it. Never bind a Mac source path on that engine or emulate arm64. CI pairs each native runner with `x86_64-unknown-linux-gnu` or `aarch64-unknown-linux-gnu` explicitly. On homevm run `cargo fmt --check`, `cargo test --locked --target x86_64-unknown-linux-gnu`, and `cargo clippy --locked --target x86_64-unknown-linux-gnu --all-targets -- -D warnings`. Fetch only these two Linux triples; lockfiles can legitimately retain other-platform entries. The ignored nftables integration test requires `--cap-add NET_ADMIN` in a disposable namespace; the ignored path-MTU test also needs outbound networking and a usable ping group range. The ignored `updater::tests::live_mullvad_relay_schema` check exercises the live public API without VPN credentials.

The runtime's host-facing requirements are kernel WireGuard, forwarding enabled with router advertisements accepted, and writable state paths if persistent storage or public-IP status files are enabled. nftables and policy routing changes are namespace-scoped. Earlier runtime probes found a direct Docker `--user 1000` launch with `NET_ADMIN` failed `EPERM`; a root `setpriv` bootstrap with `NET_ADMIN`, `SETUID`, and `SETGID` retained `NET_ADMIN` across exec as UID 1000 under `no-new-privileges`. The root-owned Docker-generated `/etc/resolv.conf` was unwritable by UID 1000, so Compose bind-mounts a loopback resolver file. CI validates both native amd64 and arm64, builds and publishes per-architecture digests, then merges them into a manifest after validation. A scheduled no-cache rebuild refreshes Debian layers; Dependabot checks Cargo, Docker, and Actions twice weekly, and `dependabot-automerge.yml` enables auto-merge on Dependabot PRs so merged updates retrigger the image build. Full live-Mullvad VPN, IPv6, and post-quantum tunnel verification still require credentials. Session-specific validation results are recorded in `HANDOFF.md`.

## Development practices

Live kill-switch validation additionally covered an operator-controlled reconnect with an established TLS stream and late-output canary counters: the old flow stalled, clear-route IPv4/IPv6 packets did not pass, and dual-stack/proxy egress recovered after restart. Shutdown probes used a test supervisor to retain eth0 and the fallback route after the Tune child exited, avoiding the false assurance of Docker removing the interface. SIGTERM retained the sealed kill switch. SIGKILL left the kernel tunnel working; deleting wg0 afterward inside only the disposable namespace blocked clear egress for both families. Explicit Prague selection and restoration of Poland-first priority passed; exhaustion-driven country failover and new native-arm64 execution were not exercised.

Compose configuration is split across two files so a multi-stack Compose environment cannot overlap variables: the project-level `.env` carries only the deployment values the Compose files interpolate — `PUID`/`PGID` (default `1000:1000`) into both the root `setpriv` bootstrap arguments and Tune's environment, with `PGID` also controlling `net.ipv4.ping_group_range`, plus `PROXY_BIND_ADDRESS` and the `*_PUBLISHED_PORT` host ports — while every application variable is read from the dedicated per-service `tune/config/tune.env` through `env_file:`. The container never receives the project-level `.env`, so other stacks sharing the project directory cannot leak variables into Tune and Tune's variable names cannot collide with theirs; Compose fails fast when the dedicated file is missing. The application itself does not switch identity. Bind-mounted state ownership must be prepared on the engine host for the chosen non-root IDs. HTTP credentials come from `HTTPPROXY_USER`/`HTTPPROXY_PASSWORD` in the dedicated file; blank defaults retain opt-in authentication. `SOCKS5=off` skips binding its listener independently of HTTP, while the override's port mapping remains declared. Environment changes require container recreation.

SOCKS5 authentication remains opt-in: both credential fields unset/blank selects the no-authentication method, while a configured pair requires RFC 1929 username/password authentication without no-auth fallback. `Socks5Settings::validate_credentials` enforces the complete pair, the 255-byte per-field wire limits, and a reachable unicast `SOCKS5_UDP_ADVERTISED_ADDRESS` (or unset); `SOCKS5_ENABLED` is accepted as a gluetun-compatible enable switch with a lower precedence than `SOCKS5`. Both environment loading and listener binding call validation, so direct library callers cannot silently create an open proxy with incomplete credentials. Tests cover no-auth defaults, partial and oversized configuration, authenticated TCP relay/cancellation, UDP ASSOCIATE relay with lazy client binding and advertised-address override, allowed-CIDR datagram drops, wrong or empty credentials, and rejection of no-auth-only clients when authentication is enabled. Direct LAN access still uses ordinary Compose bridge port publishing; no Traefik, host networking, or SSH is required.

HTTP proxy authentication follows the same pair semantics through `HttpProxySettings::validate_credentials`: both `HTTPPROXY_USER`/`HTTPPROXY_PASSWORD` unset or blank keeps the proxy unauthenticated, setting either requires both, and a username colon or control characters in either field are rejected before listeners bind. The Basic scheme match is case-insensitive; missing or wrong credentials receive `407` for GET and CONNECT without dialing the origin. Basic credentials are base64 cleartext on the browser-to-proxy path, not encryption, which the README states explicitly.

The Compose gateway enables HTTP and SOCKS5 on container wildcard listeners. `compose.override.yml`, auto-loaded by normal `docker compose` commands, publishes them on an explicitly configured `PROXY_BIND_ADDRESS` and configurable host ports. `docker compose -f compose.yml` skips that override for an existing Traefik TCP deployment with backend connectivity. The file-provider example under `traefik/config/` defines separate non-TLS TCP routers, dedicated entrypoints, and a client IP allowlist; no Traefik instance, engine socket, or production-network attachment is added. The API and metrics remain unpublished. Host networking is not supported for this namespace-managing VPN: its routes and nftables policy would otherwise be host-global. No SSH forwarding is required. Restrict access using LAN controls, the Traefik allowlist, or proxy authentication. Proxy outbound TCP sockets follow the namespace's WireGuard policy routes; status gates/cancels sessions and nftables blocks non-tunnel internet egress. SOCKS5 domain requests resolve inside the container; client-side DNS/direct UDP remains outside this TCP proxy boundary. Dev tests still publish only to homevm loopback, independently of the production LAN exposure choice.

Companions join Tune's namespace with `network_mode: "service:tune"` — the Compose service key, not the image or container name — or `--network container:<tune-container>` in plain Docker. Compose rejects `ports:`, `networks:`, and per-service `dns:` for such a service, so service ports are published on `tune` with `FIREWALL_INPUT_PORTS` where explicit admission is needed. Docker propagates the target container's `/etc/resolv.conf` into the dependent container (verified on Engine 29.9.1: the companion mounts Tune's bind-mounted loopback resolver file itself), so companion DNS follows Tune's fail-closed resolver without an extra mount; an explicit read-only mount remains the fallback for engines that do not share the file. The companion needs no capabilities and shares routes, `localhost`, and the kill switch; `depends_on` orders startup only, so companions must be recreated with Tune, and Tune's sealed shutdown keeps them from egressing in clear while the namespace survives.

Keep `README.md` user-facing and update this document when lifecycle, networking, or build assumptions change. Preserve the firewall's deny-by-default behavior across VPN reconnects, and its sealed retention across shutdown while any shared-namespace companion keeps the namespace alive. Exercise graceful shutdown and failed startup inside a disposable container network namespace. Avoid host-network testing of netfilter code.
